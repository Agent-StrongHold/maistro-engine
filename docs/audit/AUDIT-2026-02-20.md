**Methodology:** Six-domain parallel analysis (Architecture, Security, LLM/AI Safety, Testing, API Design, Operations)
**Core Question:** Can a product team and two SREs run this system in production without the original developer present?

---

## Verdict: NOT READY FOR COMMERCIAL PRODUCTION

**4 Critical · 16 Major · 8 Minor** findings across 6 domains.

The system has strong foundational design — clean Pydantic models, a well-thought-out tier system, proper constant-time auth comparison, and good security primitives (env sanitization, dangerous-tool detection, trust boundaries). However, nearly all security and operational subsystems are **defined but never wired in**. The gap between "library code exists" and "the running system enforces it" is the central theme of this audit.

## Critical Findings

### CRIT-01
**Docker Socket Mount Grants Container-to-Host Escalation**
*Domain: Security · Severity: Critical*

The maistro-engine container mounts the host Docker daemon socket, giving any code running inside — including LLM-orchestrated agents — full root-equivalent access to the host machine.

**Evidence:**
- `docker-compose.yml:24` — `/var/run/docker.sock:/var/run/docker.sock`
- `src/maistro/tools/sandbox/docker.py:101-146` — `create_sandbox()` constructs raw `docker run` commands via `asyncio.create_subprocess_exec` using this socket
- `src/maistro/security/dangerous_tools.py:61` — `/var/run/docker.sock` is listed in `BLOCKED_HOST_PATHS` but this blocklist is **never checked** during sandbox creation

**Impact:** A malicious or hallucinating LLM agent can create privileged containers, mount the host filesystem, exfiltrate secrets, or destroy other containers. Full host compromise from a single agent command.

**Remediation:** Use Docker-in-Docker with an isolated daemon, a Kubernetes Job controller, or gVisor/Firecracker for sandbox isolation. The maistro-engine process must never have direct access to the host Docker socket.

### CRIT-02
**Authentication Defaults to Disabled in Production**
*Domain: Security · Severity: Critical*

When no API keys are configured, all API endpoints operate without authentication. The default docker-compose configuration sets `API_KEYS` to an empty string.

**Evidence:**
- `src/maistro/api/auth.py:25-27` — `if not settings.api_keys: return None` silently disables auth
- `docker-compose.yml:22` — `API_KEYS=${API_KEYS:-}` defaults to empty string
- `src/maistro/main.py` lifespan handler — no startup validation that auth is configured

**Impact:** Any internet-facing deployment without explicit key configuration is a fully open API. Unauthorized users can submit tasks consuming LLM credits (potentially thousands of dollars/hour) and trigger agent execution.

**Remediation:** The application must refuse to start (or enter a locked mode) when no API keys are configured. Add a startup check in the lifespan handler. Remove the empty default from docker-compose.

---

### CRIT-03
**Webhook Signature Verification Defined but Never Called**
*Domain: Security · Severity: Critical*

The GitHub webhook handler has a signature verification function defined at `webhooks.py:19-24` but never called. The CI webhook endpoint has zero authentication.

**Evidence:**
- `src/maistro/api/webhooks.py:19-24` — `_verify_github_signature()` is defined
- `src/maistro/api/webhooks.py:27-53` — `github_webhook()` receives `x_hub_signature_256` as a parameter but never passes it to the verification function
- `src/maistro/api/webhooks.py:73-94` — `ci_webhook()` accepts any POST body with zero authentication
- Neither endpoint imports or uses `RequireAuth`

**Impact:** Anyone who discovers the webhook URL can inject arbitrary tasks. A crafted POST to `/webhooks/github` queues LLM-powered agent execution against any repository path. Combined with CRIT-01 (docker socket), this is a direct path to host compromise from a single unauthenticated HTTP request.

**Remediation:** Call `_verify_github_signature()` in the handler and reject invalid signatures. Add shared-secret authentication to the CI webhook. Both endpoints must return 401/403 on auth failure.

### CRIT-04
**All Task State Is In-Memory with No Persistence**
*Domain: Operations · Severity: Critical*

Despite having a full SQLAlchemy schema (`TaskRecord`, `MemoryEntry`, `KnowledgeNode`) and Alembic configured, no code actually reads from or writes to the database. All task state exists solely in a Python dictionary and asyncio queue.

**Evidence:**
- `src/maistro/tasks/queue.py:25-27` — `TaskQueue.__init__` creates only `self._tasks: dict` and `self._pending: asyncio.Queue`, both in-memory
- `src/maistro/memory/store.py:25-43` — `TaskRecord` schema is defined but never imported or used for persistence
- `alembic/versions/` — zero migration files exist
- The module docstring at `queue.py:1-5` claims "surviving restarts via DB recovery" — no such code exists

**Impact:** Every container restart, OOM kill, deployment, or crash destroys all task state. Customers lose in-flight work, completed results, and audit trails. No SLA is possible.

**Remediation:** Persist tasks to PostgreSQL on creation and every state transition. Implement startup recovery of incomplete tasks. Generate and apply Alembic migrations for the existing schema.

## Major Findings

### MAJ-01
**Command Injection in Sandbox Exec, Grep, and Glob Tools**
*Domain: Security · Severity: Major*

The sandbox MCP tools pass user/agent-supplied strings directly into shell commands without sanitization or escaping.

**Evidence:**
- `src/maistro/tools/sandbox/docker.py:38` — `container.exec()` passes `command` directly to `bash -c`
- `src/maistro/tools/sandbox/server.py:79` — `sandbox_glob()` interpolates `pattern` into a shell command: `` f"find /workspace -path '/workspace/{pattern}' ..." ``
- `src/maistro/tools/sandbox/server.py:93-95` — `sandbox_grep()` interpolates `pattern` into: `` f"grep -rn '{pattern}' /workspace/{path}" ``
- `src/maistro/security/dangerous_tools.py` — `is_dangerous_command()` exists but is **never called** from the sandbox execution path

**Impact:** An LLM agent can escape the grep/glob pattern context with `'; malicious_command; '` to execute arbitrary commands inside the sandbox container. While sandbox isolation limits blast radius, combined with network access (MAJ-05) this enables data exfiltration.

**Remediation:** Use `shlex.quote()` on all interpolated values. Integrate `is_dangerous_command()` checks into the sandbox execution pipeline. Consider using `docker exec` with explicit argument arrays instead of `bash -c`.

---

### MAJ-02
**Heredoc Injection in Sandbox write_file**
*Domain: Security · Severity: Major*

The `write_file` method uses a heredoc with a fixed delimiter `MAISTRO_EOF` that can be injected via file content.

**Evidence:**
- `src/maistro/tools/sandbox/docker.py:66-67` — `` f"cat > '{full_path}' << 'MAISTRO_EOF'\n{content}\nMAISTRO_EOF" ``
- If `content` contains `\nMAISTRO_EOF\nmalicious_command\n`, the heredoc terminates early and the remaining text executes as shell commands

**Impact:** An LLM agent writing file content that contains the delimiter string can execute arbitrary commands in the sandbox container.

**Remediation:** Use `docker cp` with stdin piping instead of heredoc, or use a randomized delimiter (e.g., `MAISTRO_EOF_{uuid}`).

---

### MAJ-03
**WebSocket Endpoint Has No Authentication**
*Domain: Security · Severity: Major*

The `/stream/{task_id}` WebSocket endpoint accepts connections without any authentication check.

**Evidence:**
- `src/maistro/api/ws.py:16-22` — `stream_task()` immediately calls `await websocket.accept()` with no auth check
- No import of `RequireAuth` or `verify_api_key` in the file
- Task IDs are 12-character hex strings (`uuid.uuid4().hex[:12]`) — 48 bits of entropy, enumerable under sustained attack

**Impact:** Anyone who discovers a task ID can observe real-time task progress including code review results, generated code, and error messages.

**Remediation:** Verify authentication via query parameter token or initial WebSocket message before accepting the connection.

---

### MAJ-04
**Security Subsystems Defined but Never Enforced**
*Domain: Security · Severity: Major*

Three well-designed security modules exist as library code but are never integrated into the execution pipeline:

**Evidence:**
1. **Dangerous tools** — `src/maistro/security/dangerous_tools.py` defines `is_dangerous_command()`, `is_dangerous_tool()`, `is_blocked_path()`. None are called from `sandbox/docker.py`, `sandbox/server.py`, or `git/server.py`.
2. **Trust boundaries** — `src/maistro/security/trust_boundary.py` defines `PermissionGrant`, `check_permission()`, `create_grant_for_task()`. None are called from the task runner, conductor, or any MCP tool.
3. **External content wrapping** — `src/maistro/security/external_content.py` defines `wrap_external_content()`, `detect_injection()`. Neither is called from webhooks, chat completions, or any content ingestion point.

**Impact:** The security architecture exists on paper but provides zero runtime protection. A code review that only examines the security module would conclude the system is well-protected; a runtime analysis reveals it is completely unprotected.

**Remediation:** Wire each security module into its corresponding execution path. `is_dangerous_command()` must gate `sandbox_exec()`. `check_permission()` must gate all MCP tool calls. `wrap_external_content()` must wrap all webhook payloads and user inputs before they reach the LLM.

---

### MAJ-05
**Sandbox Network Access Enabled by Default**
*Domain: Security · Severity: Major*

Sandbox containers have full outbound network access by default.

**Evidence:**
- `src/maistro/config/settings.py:50` (SandboxSettings) — `network_disabled: bool = False`
- `src/maistro/tools/sandbox/docker.py:119-120` — `--network=none` only applied `if settings.network_disabled`, which defaults to off
- No egress filtering, network policy, or proxy configured

**Impact:** LLM-generated code in sandboxes can exfiltrate customer data, contact C2 servers, or access internal Docker network services (including PostgreSQL).

**Remediation:** Default `network_disabled` to `True`. When network access is required, use a restricted network with egress filtering.

---

### MAJ-06
**Default Credentials Hardcoded Throughout Deployment**
*Domain: Security · Severity: Major*

**Evidence:**
- `docker-compose.yml:15` — `DB_PASSWORD:-maistro`
- `docker-compose.yml:17` — `LITELLM_MASTER_KEY:-sk-litellm-dev`
- `docker-compose.yml:80` — `NEXTAUTH_SECRET:-changeme-langfuse-secret`
- `docker-compose.yml:81` — `SALT:-changeme-langfuse-salt`
- `alembic.ini:3` — `sqlalchemy.url = postgresql://maistro:maistro@localhost:5433/maistro` (plaintext password committed)
- PostgreSQL port 5433 is mapped to the host — accessible with default credentials by anyone who reads the source

**Impact:** Any exposed PostgreSQL port or LiteLLM proxy is accessible with publicly known credentials. The LiteLLM master key grants access to all configured LLM API keys.

**Remediation:** Require explicit secret provisioning with no working defaults. Integrate a secrets manager. Remove plaintext credentials from `alembic.ini` (use env var interpolation).

---

### MAJ-07
**Environment Variable Sanitization Uses Blocklist, Not Allowlist**
*Domain: Security · Severity: Major*

**Evidence:**
- `src/maistro/tools/sandbox/env_sanitize.py:76-84` — `sanitize_env()` uses blocklist: `if not is_blocked_name(k) and not looks_like_secret(v)`
- `_SECRET_PATTERN` (lines 53-59) only matches specific formats: OpenAI keys, GitHub PATs, JWTs, 64-char hex
- A secret like `MY_STRIPE_KEY=rk_live_abc123def456` passes both name and value checks unblocked

**Impact:** Secrets in non-standard formats leak into sandbox containers. Combined with MAJ-05 (network access), these can be exfiltrated.

**Remediation:** Invert to an allowlist approach — only explicitly approved environment variables pass through.

---

### MAJ-08
**No Output Validation, Cost Controls, or Human-in-the-Loop**
*Domain: LLM/AI Safety · Severity: Major*

The conductor agent runs with no guardrails on what the LLM can do or how much it can spend.

**Evidence:**
- `src/maistro/agents/conductor.py:135` — `result = await agent.run(prompt)` — output is used directly with no validation
- No token budget or cost ceiling per task anywhere in the codebase
- No approval gate before the agent executes destructive operations (git push, file deletion)
- `src/maistro/agents/prompts.py:6-24` — `CONDUCTOR_SYSTEM` prompt mentions tool access ("reading and writing files", "executing commands") but includes no safety constraints, no forbidden actions, no scope limits
- Agent `retries=3` with no exponential backoff — a failing LLM call retries immediately 3 times

**Impact:** A single task can consume unlimited LLM tokens (potentially hundreds of dollars). The agent can push code, delete files, or execute destructive commands with no human review. Retries without backoff can amplify costs during provider outages.

**Remediation:** Add per-task token budgets. Require human approval for destructive operations (git push, file deletion). Add safety constraints to the system prompt. Implement exponential backoff on retries.

---

### MAJ-09
**Prompt Injection Flows Unfiltered from Webhooks to LLM**
*Domain: LLM/AI Safety · Severity: Major*

External content from GitHub webhooks flows directly into LLM prompts with no sanitization, wrapping, or injection detection.

**Evidence:**
- `src/maistro/api/webhooks.py:48-51` — PR title flows directly into `TaskCreate.description`: `` f"Review PR #{number}: {title} in {repo}" ``
- `src/maistro/api/webhooks.py:64` — Issue body (up to 500 chars) flows into task description: `` f"Investigate issue #{number}: {title}\n\n{body_text[:500]}" ``
- `src/maistro/agents/conductor.py:129-133` — Task description is placed directly into the LLM prompt with no wrapping
- `src/maistro/security/external_content.py` — `wrap_external_content()` and `detect_injection()` exist but are **never called**

**Impact:** An attacker can craft a PR title or issue body containing prompt injection instructions. Combined with unauthenticated webhooks (CRIT-03), this allows an attacker to inject arbitrary instructions into the LLM agent via a single HTTP POST.

**Remediation:** Apply `wrap_external_content()` to all webhook payload content before it enters a task description. Call `detect_injection()` and flag or reject suspicious content.

### MAJ-10
**Health Check Is Cosmetic — No Dependency Probes**
*Domain: Operations · Severity: Major*

**Evidence:**
- `src/maistro/api/health.py:15-23` — Returns hardcoded `"status": "ok"` with uptime and version. No checks for PostgreSQL, Docker daemon, or LiteLLM proxy.
- `Dockerfile` — No `HEALTHCHECK` instruction
- No `/health/live` vs `/health/ready` distinction

**Impact:** Container orchestrators cannot detect service degradation. Traffic routes to a node that cannot process tasks because dependencies are down. SREs have no automated signal until customers complain.

**Remediation:** Implement separate `/health/live` and `/health/ready` endpoints. Readiness probe must verify PostgreSQL connectivity, Docker daemon reachability, and LiteLLM proxy responsiveness.

---

### MAJ-11
**No Graceful Shutdown or Task Draining**
*Domain: Operations · Severity: Major*

**Evidence:**
- `src/maistro/tasks/runner.py:30-36` — `stop()` sets `_running = False` and immediately cancels the worker task via `self._worker_task.cancel()`
- No drain period, no checkpoint persistence, no waiting for the current `run_task()` call to finish
- No `STOPSIGNAL` in Dockerfile, no `stop_grace_period` in docker-compose

**Impact:** Every deployment or restart abruptly terminates in-progress agent work. Combined with CRIT-04 (no persistence), all work-in-progress is silently destroyed. An agent 10 minutes into a complex PR review has all work discarded with no trace.

**Remediation:** On SIGTERM: (1) stop accepting new tasks, (2) wait for in-flight tasks to complete or checkpoint (with configurable timeout), (3) persist incomplete state, (4) exit.

---

### MAJ-12
**Single-Worker Serial Architecture with No Horizontal Scaling**
*Domain: Operations · Severity: Major*

**Evidence:**
- `src/maistro/tasks/runner.py:38-47` — `_worker_loop` processes one task at a time: `next_task()` → `_execute_task()` → loop
- `src/maistro/tasks/queue.py:101-109` — `_queue` is a module-level singleton; running multiple instances creates isolated queues
- `Dockerfile:25` — `CMD ["uvicorn", ...]` with no `--workers` flag (defaults to 1)

**Impact:** Throughput is limited to one task at a time. A 15-minute code review blocks all subsequent tasks. There is no way to scale capacity by adding replicas — the architecture must be redesigned.

**Remediation:** Back the task queue with a distributed broker (Redis, PostgreSQL advisory locks, or a message queue). Enable concurrent task execution. Document a scaling strategy.

---

### MAJ-13
**No Observability Pipeline — Zero Metrics, Alerts, or Applied Tracing**
*Domain: Operations · Severity: Major*

**Evidence:**
- `src/maistro/observability/tracing.py:36` — `trace_agent` decorator is defined but **never imported or applied** anywhere else in the codebase
- No Prometheus, StatsD, or any metrics library in `pyproject.toml`
- `src/maistro/main.py:31` — structlog configured with `ConsoleRenderer()` (human-readable, not machine-parseable)
- No alerting rules, no dashboards, no log aggregation

**Impact:** SREs are blind. No way to detect degradation before customers report it. No capacity planning data. Post-incident analysis is impossible. MTTD and MTTR are unbounded.

**Remediation:** Expose `/metrics` endpoint (Prometheus format) covering request latency, queue depth, task completion/failure rates, LLM token usage. Apply `@trace_agent` to agent entry points. Switch to structured JSON logging for production.

---

### MAJ-14
**No CI/CD Pipeline, No Automated Testing in Deployment Path**
*Domain: Operations · Severity: Major*

**Evidence:**
- No `.github/workflows/`, no `Jenkinsfile`, no `gitlab-ci.yml`, no deployment scripts anywhere in the repo
- `Dockerfile:21` — `uv pip install --system -e ".[dev]"` installs dev dependencies (pytest, ruff, mypy) in the production image
- No separation between development and production builds

**Impact:** Every deployment is manual and undocumented. No gate prevents broken code from reaching production. The production image includes development tools, increasing attack surface. No rollback procedure exists.

**Remediation:** Add a CI pipeline that runs tests, linting, and type checking on every PR. Create a multi-stage Dockerfile that excludes dev dependencies from the production image. Document deployment and rollback procedures.

---

### MAJ-15
**Critical Paths Have Zero Test Coverage**
*Domain: Testing · Severity: Major*

Tests exist for auth, health, task CRUD, env sanitization, workspace validation, and security primitives. But the most critical paths are untested:

**Evidence:**
- **No conductor/LLM test** — `tests/agents/test_types.py` only tests Pydantic models, not `run_task()` or `build_conductor()`
- **No sandbox Docker test** — no test for `create_sandbox()`, `SandboxContainer.exec()`, or any MCP sandbox tool
- **No WebSocket test** — `stream_task()` is completely untested
- **No chat completions test** — `/v1/chat/completions` (the primary user-facing endpoint) is untested
- **No webhook integration test** — `tests/api/test_webhooks.py` exists but only tests routing, not the signature verification gap
- **No test coverage measurement** — no `--cov` enforcement or minimum threshold
- Tests that exist bypass auth entirely (no API_KEYS configured = dev mode)

**Impact:** The test suite provides false confidence. All tests pass, but the most critical and risky code paths have zero coverage. Regressions in the conductor, sandbox, and LLM pipeline will not be caught.

**Remediation:** Add integration tests with mocked LLM responses for the conductor pipeline. Add sandbox tests with Docker mocks. Add WebSocket and chat completions tests. Enforce minimum coverage threshold in CI.

---

### MAJ-16
**Task Runner Fakes Lifecycle Phases — REVIEWING and TESTING Are No-Ops**
*Domain: Architecture · Severity: Major*

**Evidence:**
- `src/maistro/tasks/runner.py:77-98` — After the conductor returns, the runner immediately transitions: CODING → REVIEWING → TESTING → COMPLETED in sequence with no actual review or test execution
- The status transitions happen synchronously with no work — they are purely cosmetic
- `src/maistro/agents/prompts.py:48-57` — `REVIEWER_SYSTEM` and `CODER_SYSTEM` prompts exist but are never used by any agent
- `src/maistro/agents/types.py:34-48` — `CodeOutput` and `ReviewOutput` models exist but are only populated from the conductor's single-pass output, not from dedicated agents

**Impact:** The API reports tasks as "reviewed" and "tested" when neither has occurred. Customers relying on the review score or test results are receiving fabricated data. The `review_score` in `TaskResult` comes from the same LLM call that generated the code — it is self-review, not independent review.

**Remediation:** Either implement the sub-agent pipeline (planner → coder → reviewer → tester) as designed, or honestly report the single-pass nature by removing fake phase transitions. Do not report review scores from self-review.

## Minor Findings

### MIN-01
**No TLS Configuration; All Ports Exposed in Plaintext**
*Domain: Operations · Severity: Minor*

- `Dockerfile:25` — No `--ssl-keyfile` or `--ssl-certfile` flags
- `docker-compose.yml` — Ports 8000, 4000, 3100, 3080, 5433 exposed with no TLS proxy
- All API traffic including bearer tokens and customer code traverses the network in plaintext

**Remediation:** Add a reverse proxy (nginx/Caddy) with TLS termination, or document that deployment behind a cloud load balancer with TLS is required.

---

### MIN-02
**Predictable Sandbox Container Naming with Collision Risk**
*Domain: Operations · Severity: Minor*

- `src/maistro/tools/sandbox/docker.py:103` — `f"maistro-sandbox-{id(workspace) % 100000}"`
- Python `id()` returns memory addresses that are reused after GC; modulo 100000 limits namespace to 100K values
- Name collision causes `docker run` to fail with no retry logic

**Remediation:** Use `uuid.uuid4().hex[:12]` for container names.

---

### MIN-03
**No CORS Middleware Configured**
*Domain: API · Severity: Minor*

- No `CORSMiddleware` in `src/maistro/main.py`
- Open WebUI (port 3080) making cross-origin requests to maistro-engine (port 8000) will fail in browsers

**Remediation:** Add `CORSMiddleware` with explicit `allow_origins` restricted to known frontend domains.

---

### MIN-04
**No Rate Limiting on Any Endpoint**
*Domain: API · Severity: Minor*

- No rate limiting middleware or dependency in `pyproject.toml`
- Each API request can trigger expensive LLM calls ($0.01-$0.10+ per request)
- A single client can submit thousands of tasks per second

**Remediation:** Add rate limiting (e.g., `slowapi`) to task creation, chat completions, and webhook endpoints. Return HTTP 429 with `Retry-After` headers.

---

### MIN-05
**No Pagination on Task List Endpoint**
*Domain: API · Severity: Minor*

- `src/maistro/tasks/queue.py:83-84` — `list_tasks()` returns the last 50 tasks with no cursor or offset parameter
- The API endpoint exposes no pagination controls

**Remediation:** Add `offset`/`limit` or cursor-based pagination to `GET /tasks`.

---

### MIN-06
**Dead Code: Database Schema, Alembic, and Unused Modules**
*Domain: Architecture · Severity: Minor*

- `src/maistro/memory/store.py` — Full SQLAlchemy schema (`TaskRecord`, `MemoryEntry`, `KnowledgeNode`) defined but never used for reads or writes
- `alembic/` — Configured with `env.py` and template but zero migration files
- `pyproject.toml` — `playwright`, `apscheduler`, `docker` libraries listed as dependencies but either unused or used only via CLI subprocess calls (not the Python library)
- `alembic.ini:3` — Hardcoded `sqlalchemy.url` with plaintext password, never read by the application

**Remediation:** Either implement the persistence layer or remove the dead schema code. Remove unused dependencies. If Alembic is kept, generate the initial migration.

---

### MIN-07
**Tier Config Evaluated at Import Time, Not Runtime**
*Domain: Architecture · Severity: Minor*

- `src/maistro/config/models.py:33-60` — `DEFAULT_TIERS` is a module-level dict using `os.environ.get()` at import time
- Changing `MAISTRO_TIER_*_MODEL` env vars after import has no effect
- `src/maistro/agents/conductor.py:62` — `api_key="ollama"` is hardcoded when using OpenAI provider

**Remediation:** Evaluate tier configuration lazily (e.g., inside `_get_tier_config()`) or use `pydantic-settings` to manage tier config alongside other settings.

---

### MIN-08
**Exception Details Leak to End Users in Chat Completions**
