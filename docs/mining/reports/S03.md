### /home/user/stronghold/src/stronghold/security/strikes.py:1-258
**What**: Per-user strike escalation tracker: Strike 1 → elevated scrutiny; Strike 2 → 8h lockout; Strike 3 → account disabled. InMemory impl + appeal/unlock/enable admin actions.  
**Engine coverage checked**: `/home/user/maistro-engine/packages/maistro-core/src/maistro/security/strikes.py`  

**Gap severity**: MEDIUM  
**Product-agnostic?**: PARTIAL — governance feature is product-agnostic, but Stronghold's org_id scope is Stronghold-owned.

**Findings**:
- **Missing org_id in Engine StrikeRecord** (line 36-45 Stronghold vs Engine lines 36-45): Stronghold tracks `org_id: str` to isolate strikes per tenant; Engine has `user_id` only. Per ADR-019, org-level isolation is Stronghold-specific.
- **Missing get_all_for_org() method** (Stronghold line 237-239): Stronghold has admin query to fetch all strikes in an org. Engine lacks this — product-agnostic core shouldn't enumerate orgs. **Skip (Stronghold-owned)**.
- **Logging asymmetry** (lines 136-141, 145-150, 153-157 Stronghold vs Engine 111-129): Stronghold logs org_id on violations; Engine omits. Engine logs are sufficient for single-tenant homelab context.
- **Record violation parameter asymmetry** (Stronghold line 98-106 vs Engine line 81-88): Stronghold requires org_id parameter; Engine doesn't. This is the scope difference (Stronghold-owned).
- **_recalculate_level comment** (Stronghold line 249): Stronghold explicitly notes "Don't re-lock if admin already unlocked" — this is handled identically in both but Engine lacks comment (minor docs gap).

**Action**: org_id removal is correct per ADR-019. get_all_for_org is Stronghold governance — skip. Add comment to Engine's _recalculate_level about lockout state preservation.  
**Effort**: S (doc only)

### /home/user/stronghold/src/stronghold/security/sentinel/pii_filter.py:1-142
**What**: PII scanner + redactor for tool results. Detects 13+ patterns (AWS keys, GitHub tokens, JWT, DB connection strings, IP, email, private keys, passwords). Unicode NFKD normalization for homoglyph evasion.  
**Engine coverage checked**: `/home/user/maistro-engine/packages/maistro-core/src/maistro/security/sentinel/pii_filter.py`  

**Gap severity**: MEDIUM  
**Product-agnostic?**: YES  

**Findings**:
- **Unicode normalization refactored in Engine** (Engine lines 67-77): Engine extracts `normalize_for_scan()` helper with detailed documentation explaining the invariant: *both scan and redact MUST operate on the same normalized string to avoid offset desync on compatibility characters*.
- **PII patterns identical** (lines 28-82 Stronghold vs Engine lines 23-64): Both have AWS keys, GitHub/GitLab tokens, sk- API keys, Bearer tokens, JWT, connection strings, IP addresses (with localhost exemptions), email, private keys, password assignments.
- **Stronghold inline normalization** (Stronghold line 92): `normalized = unicodedata.normalize("NFKD", text)` happens inside `scan_for_pii()` only.
- **Engine double-normalizes redact()** (Engine lines 104-122): Engine calls `normalize_for_scan(text)` again on line 117 when matches is not None. This is correct: prevents offset desync. Stronghold's redact() would apply offsets to the un-normalized original if matches were pre-computed (bug risk).
- **Docstring quality**: Engine's `redact()` docstring (lines 109-116) explicitly warns about the compatibility-character bug. Stronghold lacks this warning.

**Action**: Engine's refactored approach is superior — protects against offset-desync bugs. No action needed for Engine.  
**Effort**: S
